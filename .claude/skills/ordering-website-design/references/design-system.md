# Base pieces and token bridge

Decision (Sergio, implementation notes): new UI is built with **shadcn-style pieces on Base UI + Tailwind CSS 4**, as the `ordering-brand-system` contract requires (`references/tokens.md`: "shadcn/ui on Base UI + Tailwind CSS is required" and "Beside a legacy CSS framework"). They live next to styled-components, which stays for everything legacy. Background and measurements: [`docs/design-system/fase-0.md`](../../../../docs/design-system/fase-0.md) (§1.5 coexistence, §1.6 risks); this file does not depend on it for the rules.

Where things are (all under `src/ui/src/design-system/`): `components/` (the base pieces, listed in [The pieces](#the-pieces)), `tokens/` (the generated catalog, `aliases.mjs`, the runtime variables), `lib/` (`cn.js`, `componentVars.js`, `buttonSkin.js`: `buttonSkinCss(theme, { size, color, appearance, shape })`, the Button's look as the body of a rule for an element React does not render, such as the smart app banner's links), `preview/` (the dev-only page). **Read a piece's source for its props and variants; never use props from memory or from this file.**

## How a store's theme reaches a piece (the bridge)

1. The theme is written as `--ot-*` variables on `:root` with the helpers of THEMING.md §3, so Identity (border, shadow, motion style) already applies, and the dashboard's alias names as `--ds-*` beside them. The first paint comes from the boot `ThemeProvider`.
2. The catalog generated from the compiled theme (`pnpm theme:css-catalog`; never edit its output) maps Tailwind names to those variables in `@theme inline`, each with the schema default as the `var()` fallback. Tailwind's own palette, radii, shadows and type scale are zeroed.
3. Utilities carry the prefix **`ui:`**; there is no Preflight and Tailwind scans only `design-system/components/`. A class outside that folder is not compiled.
4. **Component values and `scope` do not travel through `:root`**: a variable on `:root` holds one global value per name. The piece reads `components.*` with the helpers (`themePart`, `themeControlHeight`, `themeIconSize`, `themeRadius(theme, key, component)`) from the React theme context, which already carries a `ComponentScope` group and crosses portals, and writes them as `--ui-<component>-<prop>` (`lib/componentVars.js`) on the **lowest common ancestor of the nodes that consume them**. Usually that is its own element, but `Input` with a prefix declares them on its `input-group`, and `Dialog` and `Sheet` on the root of their portal so that the backdrop, the viewport and the panel inherit them. Name the node that declares and the node that paints as two different things when you specify a piece. The variables of a nested control stay on that control: the close button of a dialog declares its own `--ui-button-*` on its `Button`, because on the panel they would reach every other button. Pages and features never write `--ui-*`.

Precedence of what a store configures is in [theming.md](theming.md#what-a-store-configures-and-who-wins); it is not repeated here.

## Piece or legacy primitive

- **The rule.** A control that has a base piece (the table [The pieces](#the-pieces)) uses the piece; the legacy primitive of `src/ui/src/styles/` is only for controls without one, listed in the hand-back as a migration gap.
- **Coexistence.** Migrate a control when the issue changes its look or its container. A fix that does not change the look stays legacy (that is not a violation). Never mix legacy and base versions of the same control type in one visual group: the buttons of a row, a toolbar or a dialog footer are all pieces or all legacy. A different container (a modal opened from a migrated menu) is another group.
- **Example, `ProductShare` (`src/ui/src/components/ProductShare/`).** Good: the share control is one group of pieces: the share button, the copy button and their icons are `Button shape='icon'` and the base `Icon`, and the AddToAny buttons, which a third party draws and cannot be pieces, take the box the Button gets (`componentVars(theme, 'button', …)` read for height, radius and icon size, passed to `styles.js`) so the six look alike. Bad, and not to copy: `ProductCopyURL.js` and its `styles.js`, inside a legacy `Modal`, still use the legacy `Button` and `<Icon>` with literal px and a `button { … }` descendant rule; they stay until that modal is migrated, as one legacy group. A descendant rule like that would alter a base `Button` put inside it.

### A button the store configures by slot

A store can choose size, color and appearance for one action of a group (`components.<group>.slots.<slot>`), and a screen can use two slots for the same action (checkout has `place_order` and, on the bar of small screens, `place_order_mobile`, and the props that apply depend on the cart's state). The legacy button reads them as `$size`, `$color` and `$appearance` (`slotButtonProps` in `src/utils/themeGroups.js`). The base `Button` reads `size`, `color` and `appearance` without the dollar and falls back to its own defaults when they are missing, so a migrated button that passes nothing still passes the tests in the default theme and loses what the store chose.

For each action you migrate, note in the inventory the slot that configures it, its axes, the state condition that changes which props apply and any alternate mobile slot. For a base `Button` take the public options with `slotButtonOptions(theme, group, slot, defaults)` (`src/utils/themeGroups.js`) and keep the caller's own state decisions. The close button of `Dialog` (`design-system/components/Dialog.jsx`) is an example of props that the caller decides.

- `width` (`DialogContent`, `SheetContent`): the caller's own width over the size's, written as `--ui-modal-width` on the portal: a number is the theme's, in px (`product_modal.base.width`: `width={themeValue(theme, 'product_modal', 'base.width')}`), a string a CSS width (`'80%'` in a kiosk). Without it the size's width (`size`) stands. A bottom `Sheet` is full width and ignores it.
- `closeGroup` (`DialogContent`, `SheetContent`; default `'modal'`): the group of the theme whose `slots.close` is the close button and sets the room the title leaves for it (`closeGroup='product_modal'`). Only the `modal` group keeps the piece's own defaults (md, neutral, ghost) when the theme has no slot; another group gets what its schema slot says.
- `layer` (`SheetContent`; default the sheet's own, `z-20601`): `'dialog'` inherits the containing modal's layer, or uses the standalone Dialog and legacy Popup layer (`z-20002`) when opened from the page. Base UI mounts the child portal after the parent viewport inside the parent portal, so a product Sheet with `layer='dialog'` stacks above a cart Sheet or a cart Dialog.
- A trigger outside the Sheet root uses one `createSheetHandle()` instance.
  Pass it to both `Sheet` and `SheetTrigger`. Mount the root beside the page
  when the page owns independent dialogs, keeping their layering separate.

## Reading a token in a class

- Two vocabularies, both valid: the shadcn/dashboard names (`ui:bg-primary`, `ui:text-primary-foreground`, `ui:border-input`, `ui:text-muted-foreground`, `ui:bg-card`, `ui:bg-destructive`) and the theme's own (`ui:bg-surface-alt`, `ui:text-text-muted`, `ui:p-md`, `ui:rounded-lg`, `ui:gap-sm`, `ui:shadow-md`, `ui:text-body`). Prefer the shadcn name when it exists and the meaning is the same.
- **Two names mean something else here.** `background` and `secondary` are shadcn's: `ui:bg-background` is the controls' surface (`color.surface`) and `ui:bg-secondary` the neutral fill (`color.surface_alt`). The web's own colors with those names are `ui:bg-canvas` (the page canvas, `color.background`) and `ui:bg-brand-secondary` with `ui:text-on-brand-secondary` (the editable brand color, `color.secondary`; also `brand-secondary-subtle` and `-pressed`). Open the generated `tokens/tokens.tailwind.generated.css` (each name with the `--ot-*` variable it reads) and `tokens/aliases.mjs` before using any of these; do not assume.
- Right token for the purpose (THEMING.md §5): `surface` for anything that floats, `*_text` for color as text, `on_*` for text on a fill, `primary_text` for links.
- Merge classes with the repo's `cn` (`lib/cn.js`), whose tailwind-merge knows the catalog names; a plain `twMerge` deletes classes of the same family (it dropped `text-button` size next to `text-primary-foreground` colour).
- Transitions go through the theme's motion (respects `motion_style` and reduced motion), not utility durations.
- The theme's mobile cut is 576 px and Tailwind's `sm` is 640 px: do not use `ui:sm:` for "mobile web"; use `ui:max-mobile:` (phone) and `ui:mobile:` (from 576 px up).
- Numeric utilities do nothing (`ui:inset-0`, `ui:m-0`, `ui:p-0`, `ui:min-w-0`, `ui:min-h-0`): they multiply `--spacing`, which the catalog clears, and the class generates no rule. Use the level `none` (`ui:inset-none`, `ui:m-none`) and, for a zero that is not a design value, `ui:min-w-[0]` / `ui:min-h-[0]`. jsdom does not show this; every class a piece uses must generate a rule, and a test over the pieces checks it.
- **A scale name on a size is the spacing level.** `none`, `xs` … `xxxl` resolve to `--ot-space-*` on every sizing utility: `ui:max-w-none` is `max-width: 0`, not "no limit"; `ui:leading-none` is `line-height: 0`, not 1; `ui:max-w-md` is 12 px. For no maximum, omit the class or use `ui:max-w-full`; for a line height, the text style's variable. The classes test proves that a class generates a rule, not which one: when you use a name Tailwind also has, compile it and read the declaration. `pnpm design:test` compiles every `ui:*-none` class the pieces write and fails when one that Tailwind also defines resolves to the spacing scale.
- **`ui:` only inside `design-system/components/`.** A screen never writes it: not in JSX, and not in the `className` it passes to a piece, because the screen's files are not scanned and the class compiles to nothing. A page composes with styled-components and `var(--ot-*)` (or `var(--ds-*)`) or the helpers, and puts layout (margin, grid placement, alignment) on a wrapper around the piece, never a look on the piece. The `ui-scope` guard (`pnpm design:check`) fails if `ui:` appears outside that folder; it has no baseline.

### When no token fits (TOKEN-GAP)

Go down the list and stop at the first step that fits.

1. **Not a design value** (`0`, `100%`, `min()`, a legacy z-index layer, an accessibility floor such as 44 px): a literal with a comment that says why. The [touch-area floor](#touch-area) is a standing rule. The rules that recur have a named helper in `src/ui/src/styles/Rules`, and the `literal` guard accepts `1px` and `16px` only inside that file: `srOnlyCss` and `visuallyHiddenControlCss` (text or a control only a screen reader reaches), `mobileFieldTextCss` (a phone field's text is never under 16 px, or iOS zooms), `LEGACY_LAYERS` (the z-index of the layers that predate the design system), `SPINNER_TURN` / `SPINNER_SLOW_TURN` and `PROGRESS_PULSE` (the cadence of a loop). Use them instead of writing the number. For other design-system literals, use [Recorded exceptions](#recorded-exceptions-themingmd-7). A size that is not on the scale (a width of 100, 200 or 300 px, a `max-width`) is not spacing and is not left in px: it is layout, written fluid with the recipes of `docs/design-system/px-map.md` («Maquetación fluida»: `min(100%, Nch)`, `minmax(0, 1fr)`, `dvh`, the `Dialog` sizes, `--header-height`); the `literal` guard accepts those units and still rejects a fixed `px` or `rem` inside them. The box of an image is a media level or `width: 100%` with `aspect-ratio` (px-map, «Medios»).
2. **A property of the component**: the piece's own `--ui-*` variable, or `themePart` / the component helpers in styled-components.
3. **A token of the catalog**, by name.
3b. **A legacy literal that is not a level** (10px, 15px, 20px...): use the level that `docs/design-system/px-map.md` (approved, D1) gives for that value and purpose (space, radius, border, control size, or the box of a logo, thumbnail, portrait, map or banner: `themeMedia`; a banner, map or 16:9 photo is fluid, not a level). That mapping is approved once by Sergio and is not a design decision of your issue; write `No design decision: px-map` and check it at level N1. A value that is not in the map, or a layout that visibly breaks with the mapped level, is step 4 (`TOKEN-GAP`). Never choose between two equally close levels yourself.
4. **Nothing of the above**: use the closest token, mark it `TOKEN-GAP(<issue>)` in a comment next to it, list it in the hand-back (what was needed, the token used, the effect) and keep going. Do not stop to ask, do not invent a value, do not add a token name and do not touch the schema without Sergio's authorization; a missing level is a decision of his (THEMING.md §4). When two levels are equally close (6px between 4 and 8), do not pick one: leave the literal where it is (it is legacy debt in the baseline) and list the tie as his decision.

In a class, a **reference to a variable** is allowed (`ui:h-(--ui-button-height)`, `ui:[border:var(--ui-button-border)]`) and so are the recorded exceptions; a bracketed **literal that is a design value** (`ui:p-[13px]`, `ui:bg-[#fff]`, `ui:rounded-[8px]`) never is. A Tailwind default (`ui:p-4`, `ui:text-sm`, `ui:bg-blue-500`, `ui:duration-200`) does nothing: with the defaults zeroed, a class that has no computed effect is a name that is not in the catalog.

## Using and extending pieces

- **A Button appearance used only on routes lives in `ButtonAppearances.js`.** The route passes it with `resolveAppearance`. `Button.jsx` is in the entry chunk, so it holds only appearances rendered by the header, order context or bottom navigation.
- **Use the piece, not its CSS.** The pieces of [the table](#the-pieces) cover their use; pick their variant, size and slots. Do not wrap one in `styled(...)`, and do not target its classes from a container's CSS. Utilities live in `@layer`, and **every rule outside a layer beats them, whatever the specificity**; the whole legacy app is outside layers, so a `styled(Button)` or a legacy descendant selector wins silently and detaches the piece from the store's theme (the `piece-selector` guard fails a file outside the design system that writes `[data-slot` or `--ui-`; `piece-override` fails a container whose `button`, `input` or `[role]` rule sets the look or size of a piece it renders: use the piece's prop or variant, give the container a cell that sizes the slot and let the piece fill it with `fullWidth` (a cap in `ch` takes the control's own font with `controlMeasureCss(theme, 'button' | 'input', { size })` from `design-system/lib/controlMeasure.js`, so the cap is the one the rule had on the piece), or add the variant to the piece). If the look must change for a store, it is a theme property (THEMING.md §4); if it must change for everyone, edit the piece (its variants) in `design-system/components/`.
- The reverse also happens: a legacy descendant rule of a container can alter a new piece, and so can the app's global element rules (`GlobalStyle` in `src/ui/contexts/ThemeContext`: `font-family: inherit` on inputs and buttons, the heading styles), which are unlayered. A piece's element carries `data-slot` and those rules leave `[data-slot]` out; if a piece shows the global typography instead of the theme's component one, look there first. Check each piece in the host where it is used, not only in the preview page.
- **No element or class rule may reach a piece.** Before you put a piece inside a styled container, grep that folder's `styles.js` for descendant rules on `button`, `input`, `textarea`, `svg`, `span` and `p`. A rule that matches the piece is unlayered and beats its utilities (implementation notestwo `button { … }` rules truncated a label and left icon buttons at 10×40). If everything it matched is now a piece, delete it; otherwise narrow it to the legacy control's own class. A `className` on a piece is only a hook for a test or for layout that a folder you do not own already applies (`className='add'` in `AddressList`, sized by `ProductForm`): keep it, say in a comment whose rule it is, list it as `class-hook`, and never add a new one.
- **`componentVars` is the piece's tool.** A screen reads a component's values with the helpers (`themeControlHeight`, `themeIconSize`, `themeRadius(theme, level, component)`, `themePart`). The one use of `componentVars` outside a piece is to *read* the box of a piece for a control that cannot be one (the AddToAny buttons of `ProductShare`); a screen never uses it to write `--ui-*` on its own elements.
- **A field a third party draws** (Stripe, Google Places, Mapbox, a phone input) cannot be a piece. Its container may style it, reading the Input's box read-only (`componentVars(theme, 'input')`, as `ProductShare` reads the Button's for AddToAny) so it matches the pieces beside it. That rule targets the SDK's own class inside its own wrapper, never `input { … }` of a container that also holds a base `Input`.
- Do not import `@base-ui/react` or `lucide-react` directly from a screen (the guards `base-ui-direct` and `lucide-direct` fail it). Behaviour comes from the piece; icons from `Icon`.
- **A layer that closes on an outside click.** A base `Dialog`/`Sheet` renders in its own Base UI portal, outside `#app-modals`. Use the shared `isInsideOverlay` helper (`src/utils/overlay.js`, which knows both portals) to recognize a click inside a layer, not your own `contains`, and prove it with a host test that opens the layer and clicks inside the piece. Stacking depends on DOM order (see the layers in the exceptions below).
- A control with no base piece yet: keep the legacy primitive of `src/ui/src/styles/` and list it in the hand-back as a migration gap. Adding a piece is its own change, in `design-system/components/`, reading `components.*` like the existing ones, with its tests; never one inside a page.
- **styled-components stays** for legacy code and for page composition around the pieces. It may read `var(--ot-*)` and the alias variables `var(--ds-*)` for global values (inside a `ComponentScope` or a portal it must still use the helpers for component values), and the helpers remain the way to read `components.*`.
- **Controls at the end of a choice row.** A `Choice` takes them in its `end` slot (a quantity stepper, a segmented control): they are items of the row, a click, key or press inside never toggles it, and each button reserves the 44×44 px touch area. Do not put them inside `title` or as children; a browser may not expose controls inside a checkbox or radio to assistive technology, so the row must also be usable without them.
- **What else a `Choice` row takes.** `indicator={false}` hides the indicator in one row (never shows what the theme hides); `icon` (decorative, after the indicator) and `trailing` (text at the end, part of the row: a click on it toggles the row, unlike `end`); `variant='action'`, a row that looks like a choice and only runs `onClick` (also on the current one; the arrows do not select; keep it in `role='group'`, not a radiogroup); `type='switch'`, a row of text and a switch where the whole row is the target (`role='switch'`, the track from `components.switch`). A card whose radio is its text and whose actions are out of the radiogroup: `variant='card-actions'` with `hovered` (the pointer is on the actions) and `interactive={false}`, `ChoiceIndicator` for the radio mark and `ChoiceActions` for the room of the actions (the row's padding and border room). Sources: `Choice.jsx`, `Switch.jsx`; browser spec `e2e/design/pieces-choice.spec.js`.
- **Tabs with panels and section navigation.** Use `Tabs`, `TabsList`, `TabsTrigger` and `TabsContent` together for panels. Keep the bar mounted when a panel changes. `TabsNavigation` hosts independent actions such as jumps to store sections. `MenuNavigationItem` hosts rows that enter subcategories or jump to sections in the vertical index.
- **A segmented choice (capsules of one group).** `RadioGroup segmented` with `Radio appearance='segment'` (`icon`, `label`) is the look of the tabs (`components.tabs`) on radios: pass the slot's `variant` and `size` from `slotTabsOptions(theme, group, slot)` and the `group`; use it, not `Tabs`, when the control chooses a value and has no panels (the arrows choose, role `radio`). Name the bar with `aria-label`. When choosing has a cost (the order type changes the order and can open the address form), add `activation='manual'`: the arrows only move the focus over the capsules and the bar's `SelectTrigger variant='segment'`, in the order seen (RTL included), and Enter, Space or a click choose (a tablist's rule, implementation notes M1). Inside a surface that is already the box (the header capsule) add `capsule`: the bar paints no background, shadow or line and keeps its size, inset and gap (M3). A segment that opens a list marks no option as chosen while the chosen value is another group's: `SelectRoot value={null}` with the first label as `SelectValue` children (M2).
- Focus: the app's global focus ring already applies (`!important`); do not add a second ring or remove it.

## Icons

- **New code uses the base `Icon`** (read `components/Icon.jsx` and `components/createIcon.jsx` for the props; Lucide, resolved by name through `src/ui/src/components/Icon/lucideRegistry.js`). Its default size is `1em` (it follows the text); give it a size only through the theme (`themeIconSize` or the control's `icon_size`), never a number.
- **The entry chunk.** A module is in the first load when `src/index.js` reaches it through static imports: today `Confirm`, `Overlay/lazyOverlay`, `NotFoundSource`, `Header`, `HeaderOption`, `NavigationBar`, `AddressOrderType`, `App.js` and the contexts. There, never the full `Icon` (`createIcon` with a glyph map), and the first base piece is an entry change. After touching one of them, run `pnpm build && pnpm size:entry`; a growth over the threshold is a GATE with its attribution, never a baseline update of your own. The `icon` guard enforces it: rule `entry-full-icon` fails when `src/index.js` reaches `design-system/components/Icon.jsx` through static imports. The whole registry adds about 16 kB gzip to every first load. The map of glyphs lives in `src/ui/src/components/Icon/<control>Glyphs.js` (as `orderContextGlyphs.js` and `chevronGlyphs.js`), the only place outside the pieces where `lucide-react` is imported; the control imports that map and calls `createIcon` with it. A `lucide-react` import anywhere else fails the icon guard.
- **Own brand SVGs only where the web paints the control** (Apple, Facebook, Google, Instagram, PayPal, Pinterest, Snapchat, Stripe, TikTok, WhatsApp): sign-in buttons, payment methods. They are `src/ui/src/components/Icon/brands/` (provenance in its `PROVENANCE.md`). Where a third-party kit paints the control (the share menu's AddToAny buttons), the kit's icons stay: do not redraw them, and do not add a brand icon from another library.
- **The unit that migrates its icons is the control or the group**, not the screen: a control that moves to a base piece moves its icons with it, and one control never mixes the legacy `<Icon>` (`src/ui/src/components/Icon`, react-icons) and the base one. The legacy one keeps serving every control not migrated. Do not import `react-icons` directly.
- **Every icon is a Lucide stroke (decided by Sergio, 2026-11-20).** A filled legacy glyph (`*Fill`, `*Filled`, cart, user, a map pin, an eye, a trash can, a play circle) becomes its Lucide stroke glyph through the base `Icon`: it is no longer a design question and not a reason to keep a legacy `<Icon>` or an inline `<svg>`. Only the favourite heart and the rating star take `fill="currentColor"` when their state says so. A multi-colour illustration (the credits and points wallets) is not an icon: it is an image file (`src/assets/`, exported by `src/utils/bundledImages.js`) shown with `<img>` (`alt=''` when decorative) in a box of the media scale (`themeMedia`, px-map «Medios»); never an inline `<svg>` in the code. The brand marks of the rule below stay. Lucide has no `title`; give meaning with a label on the control. The shared `ChevronIcon` (`src/ui/src/styles/Chevron`) already selects its three Lucide glyphs through `createIcon` (map in `components/Icon/chevronGlyphs.js`): use it for navigation and disclosure instead of drawing a chevron. The mask `CHEVRON_DOWN_MASK` that lists use in the same file is its own implementation, a data URI.

## Touch area

Every interactive control reserves a touch area of at least **44×44 px**.
When the theme paints it smaller, give the control a larger hit area without
changing its painted size. Use the base piece or extend the hit area with a
pseudo-element. Where a scrolling container clips the extension, reserve the
space within the container. Check actual hit testing along the edges and
between adjacent controls. The floor applies without a per-control exception.
Mark an accessibility minimum with `/* touch-target */` immediately before
the CSS declaration or the Tailwind class string. The literal guard recognizes
marked minimum dimensions and the named variables that reserve the hit area
of a control. Each marker applies locally. Spacing and painted dimensions
still read the theme.

## Verifying a piece

The levels (N0 to N3), the guards, the cheap-verification rule and "prove the gate" are in [SKILL.md](../SKILL.md#verification). Here, how.

1. **Preview page.** The dev page `design-system-preview.html` shows the pieces **in one theme at a time**, with a selector that swaps the theme without a reload (the hot theme change), and an open **portal** (dialog, sheet). The themes are the fixtures of `preview/themes.js` (read the file for the ids); `?theme=<id>` opens one. **Pick the fixture by the property it must distinguish**: `defaults` for what the schema gives, `grill`, `cafe` and `grocery` (dark and square, light and pill, light and medium corners) for color, radius and borders, and `typefaces` (its own families for title, button and field) for a piece's typography against the app's global CSS. For a hot theme change use the preview's selector, which changes the React state without a reload, and leave a portal open; the app's own selector navigates (`location.assign`), so there you check the integrated result after the navigation. It is dev-only and not part of the production build. Read `preview/main.jsx` before assuming any other parameter. Mockups of options live here, as sections (SKILL.md, step 4).
2. **The real app with a test theme: `DS_REVIEW=1 pnpm dev`.** The dev server loads `preview/devReview.js` before the app: every write to the Ordering API or to telemetry is answered with a simulated error (no orders, no payments), reads are real, and `?ds_theme=<fixture id>` (the ids of `preview/devReview.js`, as in the preview) serves that fixture as the store's theme (kept in `sessionStorage` while you navigate the SPA; `?ds_theme=store` returns the store's own; a small label at the bottom changes it). It is not in the production build. Use it to check a piece inside its real host, which is where legacy rules reach it. **It does not prove that a payment finished**: it filters fetch and XHR of its own window by method and host, and checkout can open a provider's iframe. To call payment, redirect or confirmation covered, simulate the whole order and provider cycle, frames and return included, and record the simulated order id, the number of submissions and the final route; a 403 from this mode only proves the error path.
3. **Computed-CSS assertions** (Playwright, `@playwright/test`), not screenshots alone. For each piece, in each theme of the level, at 390 and 1440 px, assert with `getComputedStyle` that background, color, border radius, border width, shadow, font family and size, height and opacity equal what the helpers return for that theme (the helpers are the oracle, never a copied literal); that a class has an effect (not the browser default); the same inside the open portal and inside a `scope` group (`product_modal`, `header`...); that after the hot switch the values follow the new theme with no reload; and that `:focus-visible` shows the ring. Add: no horizontal overflow, no console errors. What the cascade decides (a piece's typography against the global rules, a portal inheriting nothing from its opener) goes in the versioned browser spec of the design system, which compiles the sheet and loads it with `page.setContent` (no server, seconds, runs in CI), so it does not depend on a manual session.
4. **Unit tests (vitest)** assert classes, `--ui-*` variables and attributes; jsdom does not compile Tailwind (`css: false`), so they prove nothing about appearance.
5. **Build.** `pnpm build` and compare the gzip size of the entry with `main`: `pnpm size:entry` measures against the committed baseline (the branch's own, not `main`'s; `pnpm design:ratchet --base <the integration branch>` keeps that baseline from rising, and from the merge to `main` on, `main`'s), so build `main` too when the entry grows (how, and the measured difference, in `docs/design-system/guards.md`): Base UI belongs in pieces loaded on demand, and the entry takes `createIcon` with its glyphs, never the full `Icon`. Nothing from the design system may enter the production build unless a screen uses it. If the schema changed, regenerate the catalog (`pnpm theme:css-catalog`) and run `pnpm theme:verify`.
6. State what was not measured: the real theme of a store, hover and pressed states, browsers older than what Tailwind 4 supports (it uses `@layer`, `@property` and `color-mix`).

- **A test states the theme values it depends on.** A spec or fixture that needs a property on or off (`animated`, a visibility, a layout) sets it in its own theme. It never leans on a schema default, which changes (implementation notes, implementation notes).
